# 工程导师教学框架

## 教学目标

帮助学习者从“知道项目能运行”进步到“能解释、维护并迁移其中的工程思想”。围绕一条真实用户流程组织课程，而不是按文件树逐项复述。

## 六层解释法

对关键概念按顺序解释：

1. **生活类比**：用熟悉场景建立直觉，同时指出类比的边界。
2. **简单定义**：用一到两句话给出准确含义。
3. **技术原理**：解释输入、输出、状态和关键机制。
4. **项目联系**：定位到具体文件、符号或配置，并说明它在调用链中的位置。
5. **工程取舍**：说明收益、成本、替代方案和“不这样做会怎样”。设计动机没有记录时标为推断。
6. **面试问题**：要求学习者用本项目证据作答，而不是背诵定义。

## 深度控制

### Beginner（默认）

- 先解释系统边界和一条核心调用链。
- 每段只引入必要术语。
- 解释“是什么”和“在项目里做什么”。
- 提供可从代码定位的观察任务。

### Intermediate

- 增加替代技术和选择权衡。
- 解释测试边界、失败路径和数据一致性。
- 让学习者尝试修改或扩展一个局部能力。

### Advanced

- 增加性能、并发、安全、可靠性和可观测性。
- 讨论架构演进、迁移成本和组织边界。
- 区分理论最优与当前约束下的合理选择。

## 课程编排

推荐顺序：

1. 项目解决的问题和用户流程
2. 系统架构与组件边界
3. 核心技术和调用链
4. 工程过程与决策
5. 风险、教训与改进
6. 术语复习与面试训练

先讲主路径，再讲分支和异常。跨报告内容使用链接引用，不重复长篇解释。

## 阅读体验

- 用“先看全局”“一次请求发生了什么”“为什么需要它”等问题型标题引导阅读。
- 将证据账本留在内部分析中。正文不展示置信度代码、重复标签或文件路径，除非用户要求审计版。
- 不使用 `<details>` 等依赖特定 Markdown 渲染器的 HTML 标签。

- 对组件至少讲清：它接收什么、做什么、输出什么、依赖谁、失败时用户会看到什么。
- 在核心章节末尾给出“你可以继续问我”提示，并列出 2–4 个具体追问方向。

## 教学质量检查

- 每个核心概念是否连接到真实项目证据？
- 学习者是否能复述一条端到端调用链？
- 是否解释了至少一个工程权衡？
- 是否区分实现事实与设计意图？
- 类比是否明确边界，避免制造错误心智模型？
- 面试题是否能从课程正文中找到依据？
- 是否给出下一步可操作的学习任务？
