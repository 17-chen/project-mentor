# 项目考古工作流

## 1. 确定项目根目录

优先使用用户明确指定的目录。否则寻找同时包含项目说明、依赖或构建清单、源码目录及 Git 元数据的最近公共父目录。

若一个目录包含多个独立应用：

- 有 workspace 配置时按 monorepo 分析，并记录各包边界。
- 没有共同构建或部署关系时，不擅自合并；请求用户选择目标。

## 2. 安全清单

优先使用 `rg --files` 或 Git 跟踪清单。忽略：

- `.git/`
- `node_modules/`、虚拟环境和依赖缓存
- `dist/`、`build/`、`.next/`、覆盖率和编译产物
- 大型二进制、媒体和生成文件
- `.env`、私钥、凭证及会话文件

可记录上述项目是否存在，但不要读取敏感内容。

## 3. 分层读取

第一层：README、PROJECT_CONTEXT、ARCHITECTURE、DECISION_LOG、TODO、CHANGELOG。

第二层：package.json、lockfile、pyproject.toml、requirements、workspace、Docker、CI 和部署配置。

第三层：应用入口、路由、服务、数据模型、AI 客户端、核心组件和测试入口。

第四层：沿实际 import、路由调用、事件或数据流定向深入。

只在证据冲突或报告缺口仍然存在时进入第五层补充读取。

## 4. 技术确认

使用以下证据组合确认技术正在使用：

- 直接依赖声明
- 源码 import 或调用
- 框架配置
- 应用入口或运行脚本
- 部署产物或测试

仅在 lockfile 出现、仅有目录名或仅有未引用文件时，降低置信度。

## 5. Git 分析

读取 Git 状态、简短日志、分支和相关 diff。不要修改索引或工作树。

记录：

- 仓库是否为浅克隆
- 是否存在未提交变化
- 日志覆盖范围
- 可确认的演进节点
- 无法从 Git 恢复的阶段

## 6. 大型项目降级

当完整读取明显超出合理上下文时：

1. 报告文件总量和主要语言。
2. 选取每个运行时模块的入口与代表文件。
3. 沿一条核心用户流程追踪端到端调用链。
4. 对未覆盖模块明确披露采样限制。
5. 不因采样而给出全仓库级确定性结论。

## 7. 扫描产物

在进入教学阶段前形成内部摘要：

- 项目边界
- 运行时组件
- 关键配置和入口
- 核心调用链
- Git 覆盖范围
- 证据冲突
- 未知项
- 敏感内容排除说明
