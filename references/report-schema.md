# 中文学习报告 Schema

所有课程默认使用中文，并在首次出现时保留英文技术术语。默认生成单文件 `工程学习课程.md`，以适配不能可靠进行本地跨文件跳转的 Markdown 预览。只有用户明确要求时才拆分多文件。

## 默认 `工程学习课程.md`

根据项目、聊天或混合输入包含：

1. 课程说明与当前范围
2. 学习地图
3. 系统或想法的整体工作方式
4. 组件职责或对话中形成的工作流
5. 技术与术语教学
6. 工程过程和关键决策
7. 风险、未完成内容与下一步
8. 练习题和可继续追问的问题

课程必须自包含。不要使用 `<details>`、`<summary>` 或依赖打开其他本地文件的导航。默认不展示文件证据、置信度等级或审计标签；将证据保留在内部分析中。用户明确要求审计版时，才增加简洁来源附录。

## 通用要求

每份报告必须包含：

- 本章学习目标
- 基于项目证据的正文
- 已确认、合理推断与无法确认的明确区分
- 本章小结
- 建议的下一步学习内容

关键架构、技术选择、历史事件和风险必须在内部分析中可追溯，但不要让审计标签打断教学正文。不要在正文反复显示“已确认（高）”等内部标签。无法确认的信息直接写成“当前项目还没有记录……”或“从现有内容无法判断……”。

排版要求：

- 使用有信息量的二级、三级标题拆分长文。
- 每个长章节先给直觉，再讲原理和项目连接。
- 适量使用与含义一致的 emoji，避免每行都添加。
- Frontend、Backend 等英文角色首次出现时写成“前端（Frontend）”“后端（Backend）”。
- 组件职责要说明输入、处理、输出、依赖、失败表现和为什么需要该组件。
- 默认采用单文件课程，不依赖预览中的本地文件链接。

## `learning/阅读说明.md`

作为课程入口，包含：

1. 项目一句话说明
2. 报告生成范围和日期
3. 适合的学习者水平
4. 推荐阅读顺序
5. 七份报告的导航
6. 项目核心调用链概览
7. 扫描范围、忽略项与已知限制
8. 学完后应能回答的问题

## `learning/架构地图.md`

包含：

1. 系统上下文
2. 主要运行时组件与职责
3. Mermaid 架构图
4. 关键请求流或数据流
5. 数据存储与状态边界
6. 外部服务和 AI 调用边界
7. 构建与部署边界
8. 架构选择、替代方案及证据状态
9. 无法确认的连接

图中只画已确认或明确标注为推断的连接。

## `learning/技术栈教学.md`

按前端、后端、数据、AI、测试、构建与部署等实际类别组织。只讲关键技术，不逐项解释所有传递依赖。

每项技术包含：

1. 证据与状态
2. 生活类比
3. 简单定义
4. 技术原理
5. 在本项目中的作用
6. 为什么适合、可能的替代方案与取舍
7. 一个面试问题

## `learning/工程过程复盘.md`

包含：

1. 可观察到的需求与约束
2. 可由 Git 或文档确认的开发时间线
3. 当前系统的实现分解
4. 需求分析、设计、选型、编码、测试和部署各阶段的证据
5. 项目真实过程与推荐标准流程的对照
6. “不这样做会怎样”的工程解释
7. 历史缺口和无法确认项

不要在没有记录时声称 Agent 采用了某种思考过程。

## `learning/术语表.md`

按学习顺序而非字母顺序优先排列。每个术语包含：

1. 中文名称与英文术语
2. 一句话解释
3. 项目中的具体位置
4. 容易混淆的相关概念

仅收录理解本项目所必需或高价值的术语。

## `learning/风险与工程经验.md`

分开记录：

1. 已确认问题
2. 技术债或工程风险
3. 可改进项
4. 做得好的工程实践
5. 可迁移到其他项目的经验
6. 无法从仓库确认的历史教训

每项说明证据、影响、触发条件和改进方向。不要把风格偏好写成缺陷。

## `learning/面试问题.md`

按难度组织为基础、项目理解和工程权衡三组。每题包含：

1. 问题
2. 考察点
3. 参考回答
4. 项目证据
5. 一个追问

问题必须能根据本课程和项目证据回答，不要测试报告没有教授的冷门知识。

## 完成检查

生成后确认：

- 七个文件全部存在且非空。
- 没有 TODO、TBD 或未替换占位符。
- 所有 Mermaid 代码块闭合。
- 报告内部相对链接有效。
- 主要结论带状态和证据。
- 没有秘密值或完整连接串。
- “工程过程”没有把推荐流程伪装成历史。
- “错误与教训”没有把推断伪装成已发生的错误。
