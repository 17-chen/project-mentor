# 证据与反幻觉规则

## 1. 结论状态

### 已确认

存在直接、可定位且与结论一致的项目证据，例如：

- 依赖清单与实际 import 同时证明框架正在使用。
- 路由定义和调用代码共同证明一个 API 连接。
- Git 提交消息或决策日志明确记录技术选择原因。

表述：“已确认：项目使用 React 渲染前端界面。”

### 合理推断

结论由项目证据支持，但设计意图或运行时行为没有被直接记录。

表述：“合理推断：选择组件化结构可能是为了复用页面交互；仓库未记录原始决策原因。”

不得省略“推断”“可能”“看起来”等限定词。

### 无法确认

现有仓库不足以验证结论，或证据互相冲突。

表述：“无法确认生产环境是否使用该 Compose 文件；需要部署记录或平台配置。”

## 2. 证据强度

- 高：多个独立直接证据一致，或有明确决策记录。
- 中：一个直接证据，或多个间接证据一致。
- 低：仅有命名、目录结构、未引用依赖或惯例推测。

目录名、注释、README 声明和未使用依赖不能单独证明运行时事实。

## 3. 引证格式

使用相对项目根目录的路径。优先精确到代码符号或配置键：

```text
证据：`frontend/package.json` 的 `dependencies.react`；`frontend/src/main.tsx` 的 `createRoot`
```

Git 证据使用短哈希和提交主题。不要声称行号长期稳定；仅在有助于当前阅读时附行号。

## 4. 设计动机

只在以下情况下将“为什么”标为已确认：

- ADR、DECISION_LOG 或同类记录明确说明原因。
- Git 提交或 PR 说明明确记录原因。
- 源码注释明确说明约束，且实现与注释一致。

常见工程惯例只能用于解释一种可能原因，不能还原开发者心理或 Agent 对话。

## 5. Git 历史

区分：

- 可观察的提交顺序
- 当前工作区未提交变化
- 根据最终结构推测的实现步骤
- 推荐给学习者的标准开发步骤

不得将后三者混写成真实项目历史。浅克隆、压缩提交或缺失分支应列为限制。

## 6. 风险与错误

使用以下分类：

- 已确认问题：有失败测试、明确缺陷或自相矛盾实现作为证据。
- 技术债或风险：当前实现存在可解释的未来成本或故障条件。
- 可改进项：工程质量建议，不代表现有实现错误。
- 历史教训未知：没有证据证明项目曾经发生过某类错误。

## 7. 敏感信息

不要读取或输出：

- `.env`、`.env.*` 中的实际秘密值（`.env.example` 除外）
- 私钥、证书私钥、访问令牌、密码和会话数据
- 云服务凭证文件
- 完整数据库连接串或带签名 URL

可以记录敏感文件存在、环境变量名称和它们所代表的集成类别。若工具输出意外暴露秘密，不要复制到报告或回复。

## 8. 冲突与缺口

发现文档与代码、配置与部署文件或不同分支证据冲突时：

1. 列出双方证据。
2. 标记无法确认或降低置信度。
3. 说明验证所需的最小额外信息。
4. 不执行生产探测来消除不确定性。
